# Deployment

This is the minimal path to a real, publicly-reachable backend so the mobile app can be used on a physical device via Expo Go — not a full production hardening guide (see "Beyond this" at the end for what's still missing).

## Why Neon instead of Render's own Postgres

Render's free-tier PostgreSQL **expires after 30 days and is permanently deleted 14 days after that** — fine for a demo, not for anything you want to keep working. [Neon](https://neon.tech) has a genuinely free, non-expiring tier (usage-limited, not time-limited), which is why `docker-compose.yml` and the rest of these docs already treat it as a first-class option alongside local Postgres.

Redis is optional for this deploy. It's only used for the Phase 15 background jobs (alert generation, vehicle-offline detection) — the app is specifically built to degrade gracefully without it (verified with a live boot-without-Redis smoke test during that phase: the API starts fine, serves requests normally, and just logs a throttled warning). Leave `REDIS_URL` unset if you don't want to also set up Upstash/another Redis host; add it later with zero code changes when you do.

## 1. Database — Neon (free, ~2 minutes)

1. Create an account at [neon.tech](https://neon.tech) and a new project.
2. Copy the connection string it gives you (starts with `postgresql://`, includes `?sslmode=require`).
3. That's your `DATABASE_URL`.

## 2. (Optional) File storage — Cloudinary

Only needed if you'll be testing document/receipt uploads. Free account at [cloudinary.com](https://cloudinary.com) → dashboard gives you `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET`. Skip this and those three env vars stay blank — everything else works fine; only `POST /documents/upload-credentials` would return a `500` until they're set.

## 3. Backend — Render (free tier)

The repo root has a `render.yaml` Blueprint.

1. Push this repo to GitHub (already done — see the README).
2. On [render.com](https://render.com), **New → Blueprint**, connect the GitHub repo.
3. Render reads `render.yaml` and prompts for the `sync: false` variables: paste in `DATABASE_URL` (from Neon), and `REDIS_URL`/Cloudinary vars if you set those up (leave blank otherwise). `JWT_SECRET`/`JWT_REFRESH_SECRET` are auto-generated by Render (`generateValue: true`) — you never need to pick these yourself.
4. Deploy. The service's build/start commands (`npm install && npx prisma generate`, then `npx prisma migrate deploy && node src/server.js`) apply the committed migration history and start the API.
5. **Free-tier behavior to expect**: the service spins down after 15 minutes idle and takes ~30–60s to wake back up on the next request — the mobile app's first call after a period of inactivity will be slow, not broken.
6. Once live, Render gives you a URL like `https://fleet-management-api.onrender.com`. Health check: `GET https://<your-url>/api/v1/health`.
7. Seed a demo admin account (Render dashboard → your service → **Shell**):
   ```bash
   npx prisma db seed
   ```
   Logs in as `admin@demofleet.test` / `ChangeMe123!` (see `backend/prisma/seed.js`) — or register your own organization from the mobile app's Login screen once auth screens exist, or directly via `POST /api/v1/auth/register`.

## 4. Mobile app — point it at the deployed backend

```bash
cd mobile
cp .env.example .env
```
Edit `.env`:
```
EXPO_PUBLIC_API_URL="https://<your-render-url>/api/v1"
EXPO_PUBLIC_SOCKET_URL="https://<your-render-url>"
```
Then:
```bash
npm install
npx expo start
```
Scan the QR code with the **Expo Go** app (iOS/Android) on your phone — same Wi-Fi network isn't required this time, since the backend has a real public URL (unlike local dev, where the device needs your machine's LAN IP).

## Alternative: Docker

`backend/Dockerfile` builds a production image (multi-stage, non-root user, `prisma migrate deploy` on boot) for any container host (Fly.io, Railway, a VPS, etc.) instead of Render's native Node runtime:

```bash
cd backend
docker build -t fleet-api .
docker run -p 3000:3000 --env-file .env fleet-api
```

## Beyond this (not done here)

- `CORS_ORIGIN` is set to `*` for simplicity — tighten it to your actual mobile app's origin before this is anything but a personal test deploy.
- No custom domain, no managed Redis, no CDN in front of the API.
- Test gate exists (`.github/workflows/backend-tests.yml` runs the full suite, including `prisma migrate deploy`, against an ephemeral Postgres on every push) but isn't wired to block a Render deploy — deploys still happen on push to `main` via Render's own GitHub integration, independent of whether CI passed.
- An installable app file (EAS Build) or app-store distribution are separate, larger efforts — see `mobile/eas.json` for the build-profile scaffold already in place.
